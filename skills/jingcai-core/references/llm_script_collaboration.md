# LLM与脚本协作规范

> 本文档明确竞彩足球插件中，LLM（大语言模型）和脚本/工具的协作边界、决策流程和输出格式。
> 核心原则：**脚本负责确定性计算，LLM负责不确定性推理，最终决策由两者共同完成。**

---

## 一、职责边界

### 1.1 脚本/工具负责（确定性逻辑）

| 职责 | 说明 | 代表工具 |
|------|------|---------|
| 数据采集 | 从API获取赔率、资讯、赛果 | `get_official_odds`, `get_official_info`, `get_third_party_odds` |
| 概率计算 | 泊松分布、Dixon-Coles、集成模型 | `poisson_predict`, `dixon_coles`, `ensemble_predict` |
| EV计算 | 期望值、Kelly仓位、返奖率调整 | `calculate_ev`, `calculate_kelly` |
| 规则校验 | 过关上限、木桶原则、混合过关规则 | `mixed_parlay_wooden_bucket_check`, `preflight_check` |
| 历史数据校准 | 用85454场比赛校准概率分布 | `historical_calibrator` |
| 投注单生成 | 标准化投注单格式、500.com格式 | `generate_bet_slip_500` |
| 报告生成 | 数据报告、分析报告模板 | `generate_data_report_pure`, `generate_full_play_analysis_report` |

**脚本输出特点**：精确、一致、可复现、无主观判断。

### 1.2 LLM负责（不确定性推理）

| 职责 | 说明 | 参与环节 |
|------|------|---------|
| 资讯理解 | 解读8大比赛资讯（伤停、战意、赛程、天气等） | 数据采集后、分析前 |
| 异常识别 | 发现赔率异动、支持率背离、市场共识矛盾 | 价值分析阶段 |
| 策略调整 | 根据比赛特点调整分析重点、玩法权重 | 全玩法分析阶段 |
| 上下文整合 | 整合历史经验、联赛特点、球队风格 | 决策阶段 |
| 自然语言输出 | 用人类可理解的语言解释分析结果和推荐理由 | 输出阶段 |
| 异常情况处理 | 脚本失败、数据缺失、规则冲突时的兜底处理 | 全流程 |

**LLM输出特点**：灵活、有上下文、能处理异常、但可能不一致。

### 1.3 共同负责（最终决策）

| 决策项 | 脚本贡献 | LLM贡献 | 最终决策方式 |
|--------|---------|---------|-------------|
| 最佳玩法选择 | 计算各玩法EV、适配度、置信度 | 理解比赛特点、识别异常信号 | 综合评分（脚本60% + LLM40%） |
| 串关结构设计 | 计算过关上限、木桶校验、赔率乘积 | 判断比赛相关性、风险分散 | 脚本校验 + LLM调整 |
| 投注单数量 | 根据候选选项数量动态计算 | 根据比赛质量、风险偏好调整 | 脚本建议 + LLM确认 |
| 仓位分配 | Kelly公式计算理论仓位 | 根据信心度、风险偏好调整 | 脚本计算 + LLM微调 |

## 二、决策流程

### 2.1 标准决策流程

```
阶段1：数据采集
  ├─ 脚本：获取5玩法赔率、8大资讯、第三方赔率、支持率
  └─ LLM：检查数据完整性，缺失时用搜索补充，标注异常值

阶段2：全玩法深度分析
  ├─ 脚本：对每场比赛的5种玩法逐一计算概率、EV、适配度
  ├─ LLM：理解资讯，识别伤停/战意/赛程等因素对比赛的影响
  └─ 共同：LLM根据资讯调整分析重点，脚本重新计算调整后的概率

阶段3：最佳玩法识别
  ├─ 脚本：计算各玩法综合评分（EV40%+适配度30%+置信度20%+赔率合理性10%）
  ├─ LLM：识别脚本未捕捉的异常信号（如赔率异动、市场共识矛盾）
  └─ 共同：脚本评分作为基础，LLM可上下调整20%权重，输出最终排名

阶段4：投注组合设计
  ├─ 脚本：设计串关结构，校验木桶原则，计算预期奖金
  ├─ LLM：判断比赛相关性，调整投注单数量和仓位
  └─ 共同：脚本生成候选方案，LLM选择/调整后输出最终方案

阶段5：输出
  ├─ 脚本：生成标准化投注单、数据报告
  └─ LLM：用自然语言解释分析逻辑、推荐理由、风险提示
```

### 2.2 异常情况处理流程

当脚本失败或数据缺失时：

1. **脚本失败**：LLM记录错误，尝试用备用方法（如web.fetch、general_search）获取数据
2. **数据缺失**：LLM明确标注"数据缺失"，不编造数据，降低该玩法的置信度
3. **规则冲突**：LLM判断冲突原因，选择更保守的方案，标注决策理由
4. **全部失败**：LLM输出"无法完成分析"，说明原因，不强行输出推荐

## 三、输出格式规范

### 3.1 脚本输出格式（结构化数据）

```json
{
  "match_id": "2041310",
  "match": "莫尔德 vs 奥斯陆KFUM",
  "play": "让球胜平负",
  "recommendation": {
    "option": "让平",
    "odds": 4.45,
    "probability": 0.28,
    "ev": 0.214,
    "confidence": "高",
    "play_fitness_score": 0.90,
    "model_confidence": 0.50,
    "reason": "模型概率28%，赔率4.45，EV=21.4%"
  }
}
```

### 3.2 LLM输出格式（自然语言+结构化）

```
【比赛分析】莫尔德 vs 奥斯陆KFUM（挪威超）

一、数据概览
- 胜平负赔率：1.57/4.45/3.75
- 让球盘口：莫尔德让1球
- 总进球预期：2.3球

二、关键资讯解读
- 莫尔德主场强势，近5个主场4胜1平
- 奥斯陆KFUM客场防守薄弱，场均失球1.8个
- 莫尔德核心前锋无伤停，战意充足

三、玩法分析
1. 让球胜平负：让平有价值（EV+21.4%）
   - 理由：莫尔德赢1球的概率高，让平赔率4.45有价值
   - 风险：莫尔德可能赢2球以上，让平失败

2. 总进球：1球有一定价值（EV+12.1%）
   - 理由：两队防守都不错，总进球可能偏少
   - 风险：莫尔德进攻火力强，可能大比分

四、推荐
- 最佳玩法：让球胜平负-让平
- 综合评分：0.755
- 信心度：高
- 风险提示：单场比赛有偶然性，建议串关分散风险
```

## 四、LLM参与检查清单

每次分析完成后，LLM应自查以下事项：

### 4.1 数据完整性
- [ ] 5种玩法赔率是否完整获取？
- [ ] 8大比赛资讯是否获取或有替代方案？
- [ ] 第三方赔率是否获取或有替代方案？
- [ ] 支持率数据是否获取？

### 4.2 分析深度
- [ ] 5种玩法是否都进行了分析？
- [ ] 每种玩法是否计算了EV、适配度、置信度？
- [ ] 是否识别了异常信号（赔率异动、支持率背离）？
- [ ] 是否解读了关键资讯（伤停、战意、赛程）？

### 4.3 决策合理性
- [ ] 最佳玩法选择是否基于综合评分，而非只看EV？
- [ ] 串关结构是否通过了木桶原则校验？
- [ ] 投注单数量是否根据比赛质量动态调整？
- [ ] 是否有硬解码或固定阈值的情况？

### 4.4 输出质量
- [ ] 是否用自然语言解释了推荐理由？
- [ ] 是否标注了风险提示？
- [ ] 是否明确标注了数据缺失或分析局限性？
- [ ] 投注单是否使用了标准化格式？

## 五、禁止事项

### 5.1 LLM禁止事项
- ❌ 禁止编造数据（赔率、资讯、赛果）
- ❌ 禁止跳过脚本直接输出推荐（必须先让脚本计算）
- ❌ 禁止只看EV不看适配度和置信度
- ❌ 禁止硬解码固定投注单数量、串关数量
- ❌ 禁止在数据缺失时强行输出高信心推荐
- ❌ 禁止输出"稳赢""必中"等绝对化表述

### 5.2 脚本禁止事项
- ❌ 禁止在脚本中硬编码比赛特定的推荐逻辑
- ❌ 禁止固定投注单数量（应根据候选选项动态计算）
- ❌ 禁止固定串关数量（应根据过关上限和比赛质量动态选择）
- ❌ 禁止忽略LLM的调整建议（脚本应支持参数传入）
